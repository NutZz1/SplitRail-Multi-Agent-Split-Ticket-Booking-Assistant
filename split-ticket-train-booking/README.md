# Split-Ticket Train Booking Assistant — Data Package

This folder contains everything needed to start building: real railway data,
plus the synthetic layers that had to be fabricated because no free source
for them exists.

## What's real vs. synthetic

| File | Contents | Real or synthetic | Source |
|---|---|---|---|
| `stations_clean.json` | 8,990 stations: code, name, state, zone, lat/lon | **Real** | datameet/railways (github.com/datameet/railways), CC0 license |
| `trains_clean.json` | 5,208 trains: endpoints, distance, duration, which classes offered | **Real** | datameet/railways |
| `schedules_clean.json` | Full stop-by-stop schedule for all 5,208 trains, with computed halt duration per stop | **Real** | datameet/railways (halt duration derived by this package from raw arrival/departure fields) |
| `coach_compositions.json` | Ordered coach layout (e.g. S1, S2, B1, A1...) for 6 demo trains | **Real** | Manually compiled from published rake-composition guides (RailMitra, EaseMyTrip-style listings). Verify against NTES before a live demo — rake composition can change. |
| `berth_layout_rules.json` | Standard berth counts and bay layout per class (SL, 3A, 2A, 1A, CC, 2S) | **Real** | Standard, publicly documented Indian Railways coach specifications — same for every train of a given class, so not looked up per-train |
| `seat_availability.json` | Which coach/segment combinations are CONFIRMED / RAC / WAITLIST / UNAVAILABLE, for the 6 demo trains | **Synthetic** | Generated by `generate_seat_availability.py`, seeded onto the real trains/coaches/stops above |
| `train_run_calendar.json` | Which days of the week each of the 6 demo trains runs, and the explicit list of running dates between 2026-09-10 and 2026-09-25 | **Synthetic** | Generated by this package — no free dataset publishes real day-of-week/validity data (see note below) |
| `demo_subset.json` | A lightweight bundle (trains, schedules, stations, coach data, run calendar) for just the 6 demo trains — use this instead of the full files for fast local testing | Real + synthetic (extract of the above, includes `run_calendar`) | Built by this package |

**Why day-of-week validity is also synthetic:** the `day` field in the raw schedule data is the *journey day number* for multi-day trains (day 1, day 2, day 3 of travel) — it is not a day-of-week or run-frequency field. No free dataset publishes which days of the week a real train runs, so `train_run_calendar.json` assigns each demo train a run-day pattern (some daily, some specific days) and expands it into an explicit list of running dates between **2026-09-10 and 2026-09-25** — a fixed window chosen for this project's demo. Trains 16525, 15017, and 12217 deliberately do *not* run daily, so your search can be tested against a real "train doesn't run on this date" constraint.

**Why seat availability is the only other synthetic layer:** IRCTC has no free public API, and live berth-level availability cannot be scraped in bulk without an authenticated session. No dataset anywhere publishes this. Every other layer — network topology, schedules, halt times, coach composition, berth layout — is real and sourced as above.

## Important data-quality notes (found while validating this package)

- **Most listed stops are pass-throughs, not halts.** 76% of stops have arrival = departure (0-minute halt). Only real halts (>0 minutes) are meaningful split points for your search — `schedules_clean.json` already has `halt_minutes` computed per stop so you can filter directly.
- **Real halts are short.** Median real halt is ~2 minutes; only a small fraction are ≥5 minutes. Design your `SeatTransferAgent`'s minimum-switch-time threshold with this in mind — most same-train coach switches will realistically fail the feasibility check, which is expected, not a bug.
- **`day` is sometimes null** in the raw schedule (about 5% of rows) — handle this in your multi-day journey logic.
- **293 of 8,990 stations lack coordinates** (about 0.6% of stop-records are affected) — safe to drop or fall back to Option 1 (relaxed-graph Dijkstra) heuristic for those.
- **`seat_availability.json` covers only realistic bookable stops** (stations with an actual halt, plus both termini) — not pure technical pass-through points, since real tickets can't be booked to/from those anyway. This also keeps the file a manageable 1.5 MB instead of 55+ MB if every stop pair were included.

## Suggested loading order in code

1. Load `demo_subset.json` for development — it already bundles trains, schedules, stations, coach data, and the run calendar for the 6 demo trains in one file.
2. Load `seat_availability.json` separately and query it live per search (this simulates "always read availability fresh," as discussed for the booking/cancellation consistency design).
3. Load `berth_layout_rules.json` once, as static constants — same for every train of a given class.
4. When you're ready to scale beyond the 6 demo trains, switch to the full `stations_clean.json` / `trains_clean.json` / `schedules_clean.json`, and add more entries to `coach_compositions.json` by hand as needed.

## Regenerating seat availability

```
python generate_seat_availability.py
```

Uses a fixed random seed (42) for reproducibility, so your demo results are consistent across runs — useful when showing "before/after cancellation" scenarios without the availability shuffling unpredictably.

## Project setup (SplitRail code)

Use Python 3.11+ with the pinned dependencies. See the [root README](../README.md)
for the browser interface (`python web.py`) and its first-launch setup.

`railway.db` and the optional full `data_source/schedules_clean.json` are not
committed. The database builder falls back to the schedules in the committed
`demo_subset.json`, so the six-train demo works directly after cloning.

1. Optionally provide `schedules_clean.json` in `data_source/` for the full
   network. From a raw flat stop-record dump, generate it with:

       python data_source/convert_schedules.py <raw schedules.json>

   The converter groups stops by train (route order comes from the raw `id`),
   turns the `"None"` time strings into nulls, and derives `halt_minutes`,
   which is `null` at termini and `0` for a technical pass-through.
2. Build the database:

       python data_source/build_sqlite_db.py

3. Create the environment and run the tests:

       python -m venv .venv
       .\.venv\Scripts\Activate.ps1        # PowerShell
       pip install -r requirements.txt
       pytest

Source layout:

    src/data_store.py   RailDataStore - read-only access to railway.db
    src/rail_graph.py   build_graph   - min-travel-time station graph
    src/heuristic.py    RailHeuristic - admissible A* lower bound (cached Dijkstra)
    tests/              pytest suite (some graph/count checks require full schedules)
    web.py              local HTTP server and validated search adapter
    src/live_trains.py  erail.in client for currently-running services
    web/                responsive browser interface
    data_source/convert_schedules.py  raw stop dump -> schedules_clean.json

`RailDataStore.get_direct_trains(origin, destination)` lists the trains that
run a pair without a change. It respects direction (a train is only returned
when it departs the origin before reaching the destination) and excludes
technical pass-throughs at both ends, since a train that does not halt cannot
be boarded. Termini are kept: they have no halt duration but are boardable.
It reads the timetable only, so it covers every train in the database rather
than the six with simulated availability.


## Live timetable lookups

`src/live_trains.py` fetches the services currently running between two
stations from `erail.in/rail/getTrains.aspx`, which answers with a
`~`-delimited text blob rather than JSON. Parsing is separated from the
network call (`parse_between_stations` vs `fetch_between_stations`) so it is
tested against a saved response in `tests/fixtures/`.

`running_days` is a seven-character mask. **Index 0 is Monday**: train 12008
returns `1110111` and is documented as running daily except Thursday, which is
index 3. The [AniCrad/indian-rail-api](https://github.com/AniCrad/indian-rail-api)
project, which covers the same endpoint, maps index 0 to Wednesday; that would
place this train's off-day on Saturday instead.

Two deliberate differences from that project:

- It rotates `User-Agent` strings per request to avoid being blocked. This
  client sends one honest identifying `User-Agent` instead.
- Its date filter builds `new Date(YYYY, MM, DD)` with a 1-based month, which
  is off by one month. This client uses `date.weekday()` directly.

Every caller must handle `LiveLookupError` by falling back to the local
database; `web.py` does, and reports which source answered.
